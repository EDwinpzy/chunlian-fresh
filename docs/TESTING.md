## 2. 安全、上线与运维验收

- [ ] 订单归属和商家权限检查通过，不存在 IDOR（改 URL 读别人的订单）
- [ ] API 请求金额由服务器计算，客户端不能篡改金额
- [ ] 所有收款、退款、状态迁移、库存变更可追踪到唯一业务 ID
- [ ] 微信支付签名/回调/查单与退款查询都已联调
- [ ] 生产关闭 debug、错误堆栈不暴露用户隐私
- [ ] 服务器与数据库不直接暴露敏感管理端口
- [ ] HTTPS 域名与必要备案、支付资质准备齐全
- [ ] 完成数据库和上传文件**实际恢复**演练（含 binlog 时间点恢复）
- [ ] 数据库定时备份任务已就位（`infrastructure/backup/backup_db.sh`，**尚未实现**）
- [ ] 完整源代码、文档、数据库脚本归项目方所有或有明确使用权

## 3. 并发与资金一致性专项

| 编号 | 场景 | 期望 |
|---|---|---|
| C-01 | 顾客提交修订 与 商家开始配送 同时发生 | 仅一方成功；失败方收到 `ORDER_VERSION_CONFLICT` |
| C-02 | 顾客提交修订 与 顾客取消 同时发生 | 先结束待修订再按「已实付 − 已成功退款」结算 |
| C-03 | 微信支付回调并发 3 次 | 只产生一条 `WX_PAY` 流水 |
| C-04 | 双击「确认送达」 | 只产生一条 `COD_RECEIPT`，`COD_ALREADY_COLLECTED` 兜底 |
| C-05 | 补款期间「开始配送」 | `TOPUP_REQUIRED`，不改变履约状态 |
| C-06 | 修订失败后库存 | 新增预占**对称归还**，原订单保持有效 |
| C-07 | 部分退款未到账 | 保持 `PROCESSING`，不计入成功退款 |
| C-08 | 已取消 + 退款中 | 两个维度并行展示：履约已取消 + 款项退款处理中 |

> 以上 C-01~C-08 已由 `infrastructure/scripts/api-e2e-revision.php` 与
> `api-e2e-test.php` 覆盖主要分支（当前 32/32、35/35 通过）。

## 4. 不接受的"交付完成"情况

- 客户修改已支付订单功能缺失，却声称"已实现修改"
- 货到付款送达时强制标记已收款，无法保留送达未收款
- 支付、退款结果靠前端假状态，没有服务端验签查单
- 无数据库迁移与源码，升级 ShopXO 后功能无法恢复
- 没有并发与财务对账测试
- 没有可用的数据库备份与恢复手段
