# PRD｜春连鲜选 产品需求文档

> 来源：`个人卖菜小程序完整落地与双端原生架构方案V2.0.md` §0–§3
> 项目代号：**春连鲜选**（chunlian-fresh）

## 1. 项目定位

单店自营、自有固定货源、一人配送、低成本运营的个人生鲜卖菜系统。

| 项 | 内容 |
|---|---|
| 业务类型 | 单店自营 / 固定货源 / 一人配送 |
| 顾客端 | uni-app 编译微信小程序（非 H5 套壳） |
| 商家端 | Kotlin + Jetpack Compose 原生 Android APK（非 WebView 套壳） |
| 后端 | ShopXO 6.9.2 候选基线（上线前锁 commit/tag） |
| 支付 | 微信支付（在线）+ COD 货到付款 |
| 配送 | 尽快配送 / 预约送达（顾客手填地址，无地图） |

## 2. 角色与权限

| 角色 | 入口 | 权限 |
|---|---|---|
| 顾客 | 微信小程序 | 浏览、购买、修改自己未配送订单、取消、支付、查单、确认收货、售后 |
| 店主（唯一管理员） | Android APK | 商品管理、订单履约、COD 收款登记、售后、营业统计、暂停营业 |
| 后台维护者 | ShopXO Web 后台 | 初始化配置、权限配置、排障、备份、微信发货管理 |

**不做**：多商户、供应商平台、多门店、WMS、骑手管理、路线规划、实时 GPS、第三方配送、复杂优惠券积分、会员等级、拼团直播、电子面单、称重差价结算、多语言。

## 3. 不可妥协的业务规则

1. 顾客手工填写并复用收货人、手机号、详细地址，无需地图授权。
2. `asap` = 尽快安排，不承诺固定分钟数；`scheduled` = 顾客希望送达的具体日期时间。预约时间必须晚于当前时刻，**不保证绝对准时**。
3. 支付方式 `WECHAT`（在线）或 `COD`（货到付款）。**履约状态与付款状态独立**。
4. 未开始配送时顾客可反复自主修改**商品增删/数量/地址/时间/备注**或自主取消；服务端以最新有效修订版本为准。
5. 已支付订单金额增加必须补款成功才能出发；金额减少需追踪部分退款结果；取消已支付订单需发起全额或剩余可退金额退款，**防止超退**。
6. 顾客和店主同时操作时，按数据库**成功提交的先后**确定胜者；失败一方提示刷新。
7. 店主点击「开始配送」锁定顾客自助改/取消；之后只能联系店主走售后。
8. 店主「确认送达」：在线支付单直接记录送达；COD 单弹窗核对实际收款 —— **已收款并送达 / 仅送达尚未收款 / 返回**。默认不勾选收款，不伪造到账。
9. 不允许把"已送达""顾客确认收货""已付款"混成一个布尔字段。
10. 商品缺货、营业暂停时禁止新购，但不影响既有订单的数据查看和售后。

## 4. 商品定价规则

- V1 按固定规格销售：`1份（约500g）`、`1把`、`1袋`、`10枚/盒`等，每个规格是独立可售 SKU。
- 价格采用**分（整数）**存储；数量整数，非实际称重计费；标注"约重"必须有合理说明。
- 下单时固化商品名称、规格、图片地址、单价与税费/配送费快照；之后调价不影响已提交订单。
- 测试商品示例仅用于演示，不构成实际经营报价。

## 6. 订单状态机（四维，必须拆开）

| 维度 | 枚举 | 说明 |
|---|---|---|
| 履约 `fulfillment` | `PENDING` / `DELIVERING` / `DELIVERED` / `FINISHED` / `CANCELLED` | 是否已出发、是否送达 |
| 支付 `payment` | `UNPAID` / `PAYING` / `PAID` / `PARTIAL_REFUNDED` / `REFUNDING` / `REFUNDED` | 与履约无关 |
| 收货 `receipt` | `UNCONFIRMED` / `CONFIRMED` | 顾客是否确认 |
| 修订 `revision` | `NONE` / `PENDING_TOPUP` / `APPLYING` / `COMMITTED` / `FAILED` | 订单商品与金额修改流程 |

页面"待付款/待配送/配送中/已送达/已完成/已取消"为**展示映射**，不覆写 ShopXO 原订单状态表。

### 6.1 状态迁移表（核心不变量）

| 动作 | 前置条件 | 原子操作 | 用户结果 |
|---|---|---|---|
| 新建微信支付单 | 商品有货、商城营业 | 创建订单及库存预占、生成待支付单 | 待付款 |
| 微信支付确认 | 服务端查单/验签成功 | 幂等记录支付流水 | 待配送、已付款 |
| 新建货到付款单 | 商品有货 | 创建待配送单、`payment=UNPAID` | 直接待配送 |
| 编辑订单 | `fulfillment=PENDING`、本人、版本一致 | 锁行、库存差额、计算新价、修订 | 保存/待补款 |
| 取消订单 | 未配送、本人与版本一致 | 标记取消、释放库存、安排退款 | 已取消，可能退款中 |
| 开始配送 | `PENDING`，无未结补款，非取消 | 锁行，履约改为 `DELIVERING` | 禁止再自助修改/取消 |
| 确认送达 | `DELIVERING` | 记录 `delivered_at`，必要时同时核销 COD | 已送达 |
| 确认收货 | `DELIVERED` 且符合平台规则 | 独立收货记录与交易结算联动 | 已完成/待结算 |
| 退款成功 | 退款查询/验签结果为成功 | 独立退款流水入账，不重复累计 | 已退款或部分退款 |

> **货到付款已送达、未收款**时可处于"已送达 + 未付款"；系统在统计中保留应收，不自动记入实收，也不在此刻自动完成资金结算。

## 7. 顾客修改订单：金额与库存

1. 服务端确认订单属于本人且未开始配送，返回 `order_version`、最新明细、支付状态。
2. 顾客编辑后点「预览修改」，**服务器**重新查售价规则和可用库存。
   - 定价规则（默认，可配置但必须统一）：**旧有 SKU 维持原下单单价；新增 SKU 按现价；增量数量按现价**。
3. 服务端返回 `old_total_fen` / `new_total_fen` / `delta_fen` 及缺货、运费变化、退款说明；顾客点「确认变更」。
4. **COD**：原子保存新版本、变更 SKU 预占、更新应收金额；新版本立即生效。
5. **微信支付尚未付款**：使旧支付单失效/安全关闭，重新生成应付金额；对未终结的旧支付回调执行查单与补偿。
6. **微信已付款，`delta>0`**：生成待补款修订单，预占新增库存但**不覆盖已生效明细**；补款成功才原子提交新版本。超时/失败则撤销待修订与新增预占，原订单保持有效。补款期间店主不能开始配送。
7. **微信已付款，`delta<0`**：提交修订及差额退款任务，退款保持 `PROCESSING`，通过微信通知/查询确认最终成功或异常；失败进入人工队列。退款金额不可超过「实付 − 已退 − 已占用退款」。
8. **`delta=0`**：只更新地址/备注/配送时间或等价商品调整，不触发资金操作。
9. 提交成功：订单版本 `+1`、保存 before/after 快照、向 Android App 推送变更事件。
10. 出发与编辑并发时使用行锁或乐观锁 `WHERE version=? AND fulfillment='PENDING'`；只有一个提交成功，失败方重读最新状态。

**必要错误页**：商品已售罄、金额已变、订单已开始配送、补款失败、退款处理中、网络超时。所有失败必须有可重试或联系店主路径。

## 8. 取消流程

```
顾客点击取消 → 仍未开始配送?
  否 → 不允许自助取消，进入售后
  是 → 支付状态?
        COD 未收 / 微信未支付 → 取消并释放库存
        微信已支付 → 锁定订单 + 标记已取消
                    → 计算应退余额 / 幂等退款申请
                    → 退款处理中
                    → 回调或查询结果
                        成功 → 已退款
                        失败 → 报警/人工处理，保留审计
```

取消与补款中的修订冲突时，先结束/撤销待修订，再按**总已实付 − 总已成功退款**结算应退，避免漏退补款或重复退。

## 9. 商家「确认送达及收款」合并流程

- **微信支付**：`DELIVERING` → 点「确认送达」 → 二次确认 → 更新 `DELIVERED`；不再重复收款。
- **货到付款**：`DELIVERING` → 点「确认送达」 → 弹窗「应收 ¥XX.XX」，三选一：
  1. **已收款并送达**：选择现金/线下扫码/其他，默认实收为应收金额，同事务写入 `DELIVERED` + COD 收款流水 + 审计日志。
  2. **仅确认送达（未收款）**：写入 `DELIVERED`，保持 `UNPAID` 并挂待收款；之后详情页提供次级入口「补记收款」（纠错/核销入口，非日常主操作）。
  3. **返回**：不做任何变更。
- **不支持**在同一动作中只改"已收款"却不送达（异常人工改账另走有审计的维护流程）。
- 防重复：`Idempotency-Key`、唯一收款单号、事务、乐观版本校验；重复点击返回已完成结果而非重复计收。

## 10. 典型异常处理

| 场景 | 处理 |
|---|---|
| 商品缺货 | 购物车/预览提示，阻止提交不可履约 SKU |
| 付款返回成功但服务端未确认 | 展示"支付确认中"，后台查单；禁止重复新建交易 |
| 修改已付款订单增款失败 | 保持旧订单版本，撤回新增库存预占，允许再次操作 |
| 部分退款已申请但未到账 | 显示退款处理中，不记为退款成功 |
| COD 送达未收款 | 继续应收提醒，不能从统计里算已收款 |
| 顾客收菜后不确认 | 显示已送达，按交易平台允许的超时/人工规则处理，不伪造确认 |
| 安卓手机杀后台/掉网 | 恢复连接后从服务器刷新，以服务端为准 |
| 重复通知/重复操作 | 幂等处理，资金/库存不能双计 |
| 新旧地址不一致 | 店主配送时仅使用最后已提交成功的订单修订版本 |
