# PRD｜春连鲜选 产品需求文档

> 本文说明当前方案与产品规则，不等同于功能验收或生产可用证明。测试进度见 docs/TESTING.md。

## 1. 项目定位

面向单店自营、固定货源、一人配送的社区生鲜业务，控制部署成本并优先保障订单与资金记录准确。

| 项目 | 方案 |
|---|---|
| 后端 | 现有 ShopXO 服务扩展 |
| 顾客端 | Vue 3 + Vite 网页，以及 Kotlin + Jetpack Compose 原生 Android App |
| 商家端 | Kotlin + Jetpack Compose 原生 Android 管理 App |
| 支付方式 | OFFLINE_QR 线下扫码预付、COD 货到付款 |
| 配送 | 尽快配送或预约送达；顾客手填地址，不要求地图授权 |

ShopXO Web 后台用于系统维护、基础配置和排障；店主日常商品、订单、资金核对及营业管理均在商家 Android App 完成。顾客 Android 是原生客户端，不通过 WebView 加载网页。

## 2. 角色与权限

| 角色 | 入口 | 主要权限 |
|---|---|---|
| 顾客 | 网页或顾客 Android App | 浏览商品、下单、管理本人地址、配送前修改或取消、查单、确认收货 |
| 店主 | 商家 Android App | 商品和库存管理、订单履约、收款与退款核实、经营数据、只读资金流水、营业设置 |
| 后台维护者 | ShopXO Web 后台 | 初始配置、权限维护和故障排查 |

首版不包括多商户、多门店、供应商平台、WMS、骑手管理、路线规划、实时 GPS、第三方配送、复杂会员或营销体系、电子面单和称重差价结算。

## 3. 不可妥协的业务规则

1. 顾客手工填写并复用收货人、手机号和详细地址。
2. ASAP 表示尽快安排，不承诺固定分钟数；预约时间须晚于当前时间，但不保证绝对准时。
3. 支付方式仅为 OFFLINE_QR 或 COD；订单配送阶段与付款状态分别记录。
4. 服务端成功提交“开始配送”之前，顾客可以修改商品、数量、地址、时间、备注或取消；之后转为联系店主处理。
5. 对已扫码预付订单增加金额时，店主核实补款实际到账后才能提交修订；金额减少产生的退款须在实际退回后由店主登记。绝不因顾客截图或客户端回报自动记账。
6. 顾客与店主并发操作按服务端成功提交的版本决定；失败方刷新后重试。
7. COD 确认送达时由店主核对实收。仅送达未收款必须可保留并继续计入应收。
8. 订单阶段直接表示已送达与已完成；顾客确认收货时订单从已送达转为已完成，并将剩余应收自动按原付款方式记账。
9. 缺货或暂停营业时阻止新购；不影响查看和处理既有订单。
10. 写操作须幂等，金额用整数分，库存变动与订单版本保持一致。

## 4. 商品与定价

- V1 使用固定规格 SKU，例如一份、一把、一袋或一盒；数量为整数，不按实际称重计价。
- 对外金额使用整数分。下单时保存商品名称、规格、图片、单价、配送费用等订单快照；后续调价不改变已提交订单。
- 顾客修订时，旧有数量保持下单时单价，新增商品和增量数量按当前价格核算。
- 演示商品不能冒充真实库存、商品图片或经营报价。

## 5. 主要流程

### 5.1 下单与支付

顾客选择商品、地址和配送方式，服务端复核价格、库存和营业状态后创建订单。支付选择：

- OFFLINE_QR：展示店主在商家 App 上传的收款码。顾客完成线下转账后订单仍需等待店主核实实际到账，并在商家端登记。
- COD：订单进入待配送状态；送达时店主可登记实收，若仍有应收，顾客确认收货时系统自动结清并记账。

本项目不接入微信支付商户 API，也没有自动支付通知或退款回调。

### 5.2 顾客修改订单

1. 服务端确认订单属于当前顾客且仍处于待配送，返回最新版本与明细。
2. 顾客预览修改后，服务端重新核验商品价格和库存，并返回旧金额、新金额和差额。
3. 已有 SKU 的既有数量沿用原下单单价；新 SKU 和新增数量按现价核算。
4. COD 修订成功后原子更新订单明细、库存变化和应收金额。
5. OFFLINE_QR 订单需要补款时，保留当前有效明细并进入待补款。商家核实实际到账后才能提交新版本；补款失败时旧订单版本继续有效。
6. 已付款 OFFLINE_QR 订单减少金额时，新商品明细和订单总额立即生效，修订进入 APPLYING，退款流水保持 PROCESSING；此期间禁止配送和再次改单。店主核实款项已实际退回后，退款才登记成功、修订才转为 COMMITTED。金额按可退余额限制，未核实退款不计入实收。
7. 订单修订携带版本并使用幂等键。并发冲突时，失败方读取最新版本后再决定是否重试。

### 5.3 取消流程

- 未开始配送的 COD 订单可以取消并释放库存，不发起退款。
- 尚未付款的 OFFLINE_QR 订单可以取消并释放库存。
- 已收款的 OFFLINE_QR 订单取消时，先核算可退金额；只有实际退款完成并经店主核实后才登记成功。
- 取消、补款修订和开始配送并发时，以服务端版本校验和成功提交结果为准，避免重复释放库存或超额退款。

### 5.4 配送、收款与退款

确认送达时，COD 由店主选择“已收款并送达”或“仅送达未收款”。默认不选中已收款。已送达未收款订单继续显示应收；后续补记收款必须对应实际到账。

扫码预付款、修订补款与退款都必须先核对实际资金变化，再由店主记录。减量修订的新明细和总额可以先生效，但退款在实际退回并经店主核实前保持处理中，不计入成功退款或实收。系统不能将二维码展示、截图或顾客口头反馈视作资金到账。

### 5.5 资金流水查询

商家 App 的经营统计入口提供只读资金流水页，供店主核对已登记的收款、补款和退款。列表显示流水类别、订单号、发生时间、金额与状态；退款金额使用负数表示。页面汇总成功入账、成功退款和净额，处理中流水单独展示且不计入成功汇总。列表支持分页和刷新，不提供流水编辑、删除或资金登记操作；实际到账和退款仍须在线下核实后，在订单操作中登记。

## 6. 订单状态模型

订单记录配送阶段、支付状态与修订状态：

| 维度 | 主要状态 |
|---|---|
| 订单阶段 order_status | PENDING、DELIVERING、DELIVERED、FINISHED、CANCELLED |
| 支付 payment | UNPAID、PAYING、PAID、PARTIAL_REFUNDED、REFUNDING、REFUNDED |
| 修订 revision | NONE、PENDING_TOPUP、APPLYING、COMMITTED、FAILED |

顾客确认收货会把 `DELIVERED` 推进为 `FINISHED`，记录 `received_at`，并将尚未入账的余额按所有付款方式自动写入 `CUSTOMER_RECEIPT` 成功流水，统计时归入订单原付款方式。已足额入账的订单不会重复产生流水；退款处理中时支付状态仍为 `REFUNDING`。商家在确认送达时已登记的 COD 实收会抵扣该余额。

COD 已送达未收款是有效状态：顾客确认收货前款项保持未付、应收继续存在，不计入实收。顾客确认收货时会自动结清剩余应收；退款仅在实际退回并由店主确认后登记。
